# 扩展路线图

你要加的四类数据。好消息：**事件表的 schema 已经能装下全部**，不需要改表结构：

```sql
events(ts_utc, day_local, domain, metric, value_num, value_text, source, meta_json)
```

每一类只是往 `domain` 里加一个新值。可视化那边（Grafana / Dataview）自动就能读到。

## 1. 手机使用频率（应用打开 / 屏幕点亮）

**难度**：★★☆ ｜ **依赖**：Tasker 或 MacroDroid

### 数据从哪来

Android 的 **Usage Access** 权限能让自动化 App 拿到「当前前台应用」和「屏幕状态变化」。

### 已有的基础设施

`/ingest/phone` 端点**已经写好并验证过**（冒烟测试里覆盖了）。它接受：

```json
{"ts_utc":"2026-10-13T12:00:00Z","domain":"phone","metric":"unlock",
 "value_text":"com.tencent.mm","source":"tasker"}
```

### 要做的事

**Tasker 侧**（两个 Profile）：

| Profile | Trigger | Action |
|---|---|---|
| 屏幕点亮 | `Event → Display → Display Unlocked` | HTTP Request → POST `/ingest/phone`，`metric: "unlock"` |
| 应用切换 | `Event → App Changed`（需 Usage Access） | 同上，`metric: "app_switch"`，`value_text: %app_package` |
| 屏幕亮 | `Event → Display → Display On` | 同上，`metric: "screen_on"` |
| 屏幕灭 | `Event → Display → Display Off` | 同上，`metric: "screen_off"` |

> 后两个是**屏幕使用时间**的来源（`Σ(screen_off − screen_on)`，实测不是推的），
> 同时把「各应用时长」从下界变成准确值 —— 没有 `screen_off`，
> 当天最后一个应用的时长测不出来。

Header：`X-API-Key: <config 里的 key>`、`Content-Type: application/json`

> ✅ `%TIMES` 是 Unix **秒**，中继直接收，**不用转** —— 写 `{"ts":%TIMES,...}` 即可。
> （早先的版本要求手机侧转成 ISO8601，得挂一段 JavaScriptlet；改到服务器上做
> 一次比在 Tasker 里做可靠得多，所以中继现在两种都认。）

**代码侧** —— ✅ 已完成

1. `normalize.PHONE_APPS`：应用包名 → 可读名字（`com.tencent.mm` → `WeChat`）。
   包名和应用名**两种都认** —— Tasker 的 `%app_package` 给的是包名，
   `%PACKAGE` 给的是包名，看任务怎么配的。不在表里的原样保留，不会丢。
   想加应用就改这一张表。
2. `normalize.summarize_phone()`：把原始事件汇总成解锁次数、切换次数、
   首末解锁时间、以及**用得最多的应用**（按前台时长排序）。
   渲染进 `02-Phone/<日期>.md` 和日记的 `## Phone` 段。

> ⚠️ **「使用最久的 App」是推导的，不是上报的。**
> Tasker 的 App Changed 事件只有时间戳、没有时长。两条相邻切换之间的
> 时间差就是前一个应用的前台时长 —— 但要**用解锁事件截断**：
> 解锁意味着屏幕之前是灭的，中间那段不属于任何应用。没有这道截断，
> 「切到浏览器 → 锁屏放口袋 → 两小时后再解锁」会把两小时都算给浏览器。
>
> 所以**「Display Unlocked」那个 Profile 不是可选项**，它是前台时长能不能算准的前提。
>
> 另外这个数字是**下界**：当天第一个和最后一个应用没有下一跳，测不出时长。
> 代码和日记提示里都标了「不是手机总使用时长」，别拿它当屏幕时间汇报。

**手机侧** —— 还没做，需要你在 Tasker 里配。完整步骤见
`docs/分阶段落地.md` 阶段 5，服务器侧部署见 `server/phone-relay/README.md`。

> ⚠️ **上报地址是服务器，不是本机。**
> 本机是笔记本，一天只醒几小时（实测 24 小时里只有 3.4 小时），
> 而 Tasker 的 HTTP 请求**没有队列** —— 电脑睡着时那一发直接失败，数据静默丢失。
> 服务器 24 小时开着，手机只对它说话，笔记本 23:00 用
> `collect_phone_events.py` 来拉。跟位置数据（Dawarich）是同一套形状。

### 断线风险

这依赖 Tasker 常驻。**Android 同样会杀它** —— 需要和 GPSLogger 一样设「忽略电池优化」。

## 2. 手机消费记录

**难度**：★★★ ｜ **依赖**：Firefly III（自托管）

### 三个选项

| 方案 | 优点 | 缺点 |
|---|---|---|
| **Firefly III** | 有官方 REST API、Personal Access Token、自动导入 | 又一个容器；要手动/半自动录入账单 |
| **Tasker 解析支付通知** | 全自动 | 脆——App 改通知格式就废；且只能拿到通知里有的信息 |
| **手动** | 零风险 | 靠自觉，通常坚持不下来 |

**推荐 Firefly III。** 它在你的 Linux 服务器上跑，和 Dawarich 一样，通过 Tailscale 访问。

```bash
# 服务器上，和 Dawarich 并列
cd /opt && mkdir firefly && cd firefly
# 官方 compose: https://docs.firefly-iii.org/how-to/firefly-iii/installation/docker/
docker compose up -d
```

拿到 Personal Access Token 后，写一个 `collect_finance.py`，把当天支出汇总成一条事件：

```
domain=finance, metric=daily_spend, value_num=金额, value_text=主要分类
```

> ⚠️ `value_num` 是浮点。**金额不要用浮点存大额** —— 但日汇总级别没问题。
> 如果需要精确到分，把整数分存进 `value_num`，在 `meta` 里标 unit。

## 3. GitHub Activity

**难度**：★☆☆ ｜ **最容易做的一个**

### 数据源

`GET https://api.github.com/users/{user}/events/public` —— 公开事件，**不需要 token**

要看私有仓库的话需要一个 classic PAT（scope: `repo`），放环境变量。

### 事件 → 记录的映射

GitHub 的 event type 天然对应「今天干了什么」：

| GitHub event | 归一化成 |
|---|---|
| `PushEvent` | `metric="commit"`, `value_num=commits`, `value_text=repo` |
| `PullRequestEvent` | `metric="pr"`, `value_text=repo#number`, `meta.action=opened/merged` |
| `IssuesEvent` | `metric="issue"` |
| `IssueCommentEvent` / `PullRequestReviewEvent` | `metric="review"` |
| `ReleaseEvent` | `metric="release"` |

写 `collect_github.py`，domain 用 `dev`。

### 为什么值得做

这是**唯一能自动量化「我到底在写什么」的数据源**。屏幕分类只能告诉你「在 VSCode 里待了 3 小时」，
GitHub 能告诉你「推了 4 个 commit 到 lifelogging，开了 1 个 PR」。两个合起来日记才有说服力。

## 4. AI agent 使用与 token 用量

**难度**：★★☆ ｜ **部分已经有了**

### 现状

**本流水线自己的调用已经在记录了** —— `state/cost_ledger.jsonl`（带 hash 链防篡改），
每周日 `reconcile_cost.py` 会把汇总写进 events 表（`domain=ai, metric=cost_reconcile`）。

### 缺的是：你在别处用 AI 的用量

比如 Claude Code、ChatGPT、Cursor 等。

| 来源 | 怎么拿 |
|---|---|
| **Claude Code** | 原始数据在 `~/.claude/projects/**/*.jsonl`，每条带 token 用量。现成工具 `ccusage`（npx）能出 `--json` |
| **Anthropic API** | Admin API `/v1/organizations/usage_report/messages`（需 Admin key） |
| **DeepSeek** | 只有余额接口，没有明细 —— 这也是为什么我们自己做台账 |
| **OpenAI** | Admin API `/v1/organization/usage/completions`（需 `sk-admin-` key） |
| **本机其他工具** | 各自想办法；拿不到就用 LiteLLM 网关兜住 |

### 统一成什么形状

```
domain="ai"
  metric="tokens"   value_num=token 数, value_text=model 或工具名, meta.direction=in/out/cache
  metric="cost"     value_num=金额,   value_text=币种,       meta.tool="claude-code"
  metric="calls"    value_num=次数,   value_text=工具名
```

写一个 `collect_ai_usage.py`，每天扫一遍各处日志，汇总进事件表。

### 这件事的真正价值

汇总之后你能回答一些有意思的问题：

- 「这个月 AI 花了多少钱，换来多少产出」—— 和 GitHub 的 commit 数做相关分析
- 「哪个项目的 AI 成本最高」—— 笔记本流水线本身的成本是可控的（每天 ¥0.003）
- 「token 花在输入还是输出」—— 我们已经实测出**输出占 93%**

## 实施顺序建议

| 顺序 | 项目 | 理由 |
|---|---|---|
| **1** | GitHub Activity | 最容易，收益立刻可见，不需要新服务 |
| **2** | AI 用量汇总 | 数据已在手边（Claude Code 日志），做起来快 |
| **3** | 手机使用频率 | 需要 Tasker 配置 + 包名映射，中等工作量 |
| **4** | 消费记录 | 要新起 Firefly III 容器，且录入习惯要养成 |

**但这四件事之外，有件更重要的事：先实跑一周。** 目前所有数据都是今天几小时的碎片，
你不知道这套日记对你到底有没有用。**如果一周后发现你根本不看，那这四个扩展就是白做。**

## 一个架构上的提醒

现在所有东西都往 `events.db` 这一张表里塞。这在数据量小的时候没问题，但要留意：

- 手机解锁事件可能一天几百条 —— 一年就是十万级。SQLite 扛得住，但要建好索引（已有 `idx_events_day`）
- **别把原始高频数据全量灌进来**。手机解锁的原始事件有意义，但「每 5 秒 GPS 点」没有 ——
  Dawarich 自己存着就行，我们只取日汇总

判断标准：**这条数据你三个月后还会去查吗？** 不会的话，存汇总而不是原始值。
