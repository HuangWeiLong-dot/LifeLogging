# 分阶段落地

每个模块都给了「最小可行」和「完整」两档。**不要一上来就全上** ——
这套系统的失败方式从来不是技术不够，而是第一周就放弃了。

---

## 阶段总览

| 阶段 | 内容 | 耗时 | 你能得到什么 |
|---|---|---|---|
| **0** | 环境 + 库结构 | 30 分钟 | Obsidian 里能看到空模板和面板 |
| **1** | 电脑端采集 + 日记闭环 | 2–3 小时 | **每晚自动出日记** ← 这是全部价值的一半 |
| **2** | 位置轨迹 | 1 小时 | 日记里出现「在哪待了多久」 |
| **3** | 手环健康 | 1–2 小时 | 睡眠/步数进日记，能做相关性分析 |
| **4** | 成本控制加固 | 1 小时 | 预算硬封顶 + 对账 |
| **5** | 手机端细粒度事件 | 2 小时 | App 切换、解锁次数 |

**建议：做完阶段 1 就先停一周。** 用一周再看要不要继续 ——
很多时候你会发现日记本身已经够用，位置和健康只是锦上添花。

## 阶段 1 · 电脑端 + 日记闭环（2–3 小时）

### 1a. 最小可行

**装 ActivityWatch** —— 电脑端的**唯一**数据源（本方案不含录屏录音）

```powershell
winget install ActivityWatch
# 或者下载安装器：https://activitywatch.net/downloads/
```
装完确认采集器在跑：`aw-watcher-window`（窗口标题）、`aw-watcher-afk`（是否在电脑前）。
验证：浏览器打开 `http://127.0.0.1:5600`，能看到数据。

> ✅ **已为你执行**：ActivityWatch 0.14.1 已安装、已启动、已设开机自启。
> 这一段可以直接跳过。注意它只在**窗口切换时**写记录，
> 刚装好没数据是正常的，正常用几分钟就会填满。

**启动事件表中间件**
```bash
python -m middleware.events_api
# 另开一个窗口
curl -H "X-API-Key: <config里的key>" http://127.0.0.1:18787/health
```

**跑一遍采集 + 归一化**
```bash
python scripts/collect_desktop.py --date today
python scripts/normalize.py --date today
```

打开 `state/timeline-<日期>.md` 看一眼。**这一步是整个系统最该你亲自看的**：
分类对不对？`## 规则没认出来的应用` 里有没有高频应用？有的话加进
`normalize.py` 的 `APP_RULES`。每加一条，每天就少喂一点数据给 LLM。

**配 AI**：`config.yaml` 里已设好 `ai.provider: deepseek`，只需要给 key：
```powershell
setx DEEPSEEK_API_KEY "sk-..."      # 永久，新开窗口生效
# 或者只在当前窗口：
$env:DEEPSEEK_API_KEY="sk-..."
```

> DeepSeek 的缓存是**自动**的（磁盘前缀缓存），不需要 cache_control 标记。
> 前缀 ≥1024 token 且逐字节匹配就自动命中，命中价约为未命中的 1/50。
> 所以系统提示词越长越稳定越省钱 —— **不要往里拼日期**（每天变一次 = 永远不命中）。
> 实测：第二次调用就命中了 1152/1324 的输入 token。

**生成日记**
```bash
python scripts/generate_journal.py --date today --dry-run   # 先看输出
python scripts/generate_journal.py --date today             # 满意了再写
```

**验收**：`vault/05-Journal/2026-10-13.md` 里出现带行内字段的时间开销和今日复盘。

## 阶段 3 · 手环健康（1–2 小时）

这一段**必须写中间件**，因为 Gadgetbridge 完全没有 REST API。

1. 手机装 **Gadgetbridge**（F-Droid），配对好手环
2. `Settings → Automations → Auto export database`，设每小时
3. 用 Tasker 把导出文件**传到服务器上的中继**（`server/phone-relay/`），
   本机 23:00 用 `scripts/collect_watch.py` 取回。
   > 一开始这里写的是 Syncthing。改成走中继的理由：
   > 本机是笔记本，一天只醒几小时，手机传文件那一刻它多半没开 ——
   > 直连必然丢一大半。而中继**已经在了**（手机使用事件走的就是它），
   > 复用比再装一个常驻 App 划算。
   > 而且 Gadgetbridge 的导出是**全量快照**，漏传一次不会丢数据，
   > 所以「Tasker 没有队列」这个短板在这里不成立。
4. `config.yaml` 里设 `sources.gadgetbridge.enabled: true` 和 `db_path`

```bash
python -m middleware.ingest_gadgetbridge --date today --dry-run
```

**第一次跑必须用 `--dry-run`**：不同手环的表名列名都不一样，
脚本靠「按列名匹配」找表，先看它选中的表对不对。
如果匹配错了，看脚本打印的「候选表」列表，手动改 `METRIC_COLUMNS`。

⚠️ 脚本对睡眠时长做的是**估算**（非零采样数 × 采样间隔），
因为 Gadgetbridge 存的可能是采样数而不是分钟。标注了 `estimated_minutes`。
要精确值的话，用 Gadgetbridge 的 Health Connect 集成，走 Android 那侧。

### Garmin（Forerunner 235 实测记录）

**Gadgetbridge 支持 Garmin**，所以不用另写采集器。但 2026-10-14 拿真实导出
逐张表看过之后，有几点和上面的描述不一样：

| | |
|---|---|
| ✅ 拿得到 | **步数**、**心率**（均值 / 最低）、**跑步**、电量、静息心率、静息代谢率、强度分钟 |
| ✅ 跑步（已接） | `BASE_ACTIVITY_SUMMARY`，实测那台有 73 次。每次都带距离、配速、心率区间、<br>爬升、卡路里、**VO2max**、训练效果、恢复时间 |
| ❌ **拿不到** | **睡眠**。全库 181 张表里，**没有任何非空的 SLEEP 表** |

> **睡眠拿不到不是配置问题，是那条路上确实没有。** 要睡眠只能走
> Garmin Connect（云，违反本项目「不依赖第三方云」的原则），或者换设备。
> 别再花时间调睡眠了。

**实测确认、并已据此改掉脚本的两件事：**

1. **`STEPS` 是当天累计值**，不是每分钟增量（实测 3654 → 4958 → 4990 → 4990）。
   `to_events` 用 `max()` 取当天总数，这一点原来就是对的。
2. **选表必须优先看有没有数据，不能只看匹配到几个指标。**
   Gadgetbridge 的库会把**所有**设备的 schema 都建出来（小米 / 华米 / Garmin…），
   没接的设备就是一张空表。实测：空表 `HUAMI_EXTENDED_ACTIVITY_SAMPLE`
   匹配 5 个指标，真数据表 `GARMIN_ACTIVITY_SAMPLE` 只匹配 2 个 ——
   按指标数排会选中空表，然后打印「没数据，可能没戴表」，
   **一个错的解释掩盖了一个真 bug**。已改成 `(有数据, 指标数)` 排序。
3. **锻炼会话那张表的时间列叫 `START_TIME`，单位是毫秒**（不是 TIMESTAMP / 秒）。
   按秒解释会**静默**落到 1970 年 —— 它照样是个合法时间戳，不会报错。
   也因为它没有 TIMESTAMP 列，它**不在**候选表里，必须单独读，
   而且不能因为候选表为空就把它一起跳过。

**跑步数据怎么分流**（这个分法是刻意的）：

| 事件 | domain | 去向 |
|---|---|---|
| 每次锻炼（含全部细节） | `fitness` | 只进事件表给可视化用，**故意不进日记** —— 否则 `## Health` 里会出现一行没头没尾的「workout: 20.0」 |
| 当天汇总 `run_km` / `run_minutes` / `run_count` / `vo2max` | `health` | 进日记的 `## Health` 段 |

> ⚠️ **配速存的是秒**（`run_pace_s_per_km: 283.0`）。喂给模型前必须换算成
> 「283 s/km (= 4:43 per km)」，否则模型会写成「283 配速」或者干脆跳过。
> 见 `generate_journal._fmt_health()`。

**替代路径**：如果不想折腾 Syncthing，用 Gadgetbridge 0.89+ 的
Health Connect 集成 + Health.md App 导出 JSON → 直接 POST 到 `/ingest/gadgetbridge`。

## 阶段 4 · 成本控制加固（1 小时）

到这里你已经在花钱了，该上护栏。

**第一层（必做）**：Anthropic 控制台设 spend limit。这是唯一真正可靠的封顶。

**第二层（已内置）**：`config.yaml` 的 `budget` 段
```yaml
budget:
  currency: "CNY"
  daily_cap: 3.00
  warn_pct: 0.80
  fail_closed: true
  max_llm_calls_per_run: 8     # 防止 agent 循环跑飞（超支第一大原因）
```

**成本实测**（deepseek-flash，一次完整日记）：**¥0.0023–0.0642，平均 ¥0.0206**，
其中 **97% 花在输出 token 上**，输入只占 3%（自动前缀缓存把输入命中价压到
未命中的 1/50）。所以省钱的方向是控制输出长度和推理 token，
而不是继续优化输入缓存。按每天一篇算月化 **约 ¥0.6**。

⚠️ 这个数**随输出长度变，不是常数**。早期文档写的「约 ¥0.003」是第一次测试
（输出 392 token）的数字；后来正文变长到平均 3700 token，涨了约 10 倍。
核对随时用 `python scripts/cost_guard.py report --days 30`。

**第三层（可选）**：LiteLLM 网关
```bash
cd docker/litellm
cp .env.example .env && 编辑
docker compose up -d
```
⚠️ **不接 Postgres 的话 `max_budget` 是 fail-open** —— 静默放行超额请求。
这就是 compose 里带 `litellm_db` 的原因。

**对账**：
```bash
python scripts/cost_guard.py check-deepseek    # 余额 + 还能用几天
python scripts/reconcile_cost.py --days 7 --write-vault   # 台账完整性 + 落盘报表
```

> ⚠️ DeepSeek **没有** Anthropic 那种按日账单 API，拉不到明细。
> 所以对账思路是「余额 + 本地台账」互相印证，而不是逐条比账单。
> `reconcile_cost.py` 的 hash 链校验才是这里的重点 ——
> 台账是全系统唯一碰钱的数据，被改过必须能发现。

## 阶段 5 · 手机端细粒度事件（2 小时）

**Android + Tasker**：

1. 装 Tasker，给 `PACKAGE_USAGE_STATS` 权限（用 Tasker Permissions 这个辅助 App 免敲 ADB）
2. 建 Profile：
   - `Event → Display → Display Unlocked` → Task → HTTP Request
   - `Event → App Changed`（需 Usage Access）→ 同样发 HTTP Request
3. HTTP Request 配置：
   - Method: POST
   - URL: `http://<服务器Tailscale地址>:8788/ingest/phone`
   - Headers: `X-API-Key: <中继的key>`、`Content-Type: application/json`
   - Body:
     ```
     {"ts":%TIMES,"domain":"phone","metric":"unlock","source":"tasker"}
     ```
   - `%TIMES` **直接写就行，不用转** —— 服务器端的中继收 Unix 秒并替你
     转成 ISO。比在 Tasker 里挂 JavaScriptlet 可靠得多。

> ⚠️ **发服务器，不是发本机。** 本机是笔记本，一天只醒几小时（实测 24 小时里
> 只有 3.4 小时），而 Tasker 的 HTTP 请求**没有队列** —— 电脑睡着时那一发直接
> 失败、数据静默丢失。服务器 24 小时开着，手机只对它说话，
> 笔记本 23:00 跑流水线时用 `collect_phone_events.py` 来拉。
>
> 服务器侧的部署步骤见 **`server/phone-relay/README.md`**。

> ⚠️ Tasker 的响应存在 `%http_data` 里但**不会自动解析 JSON**，
> 要 JavaScript action 手动 `JSON.parse`。调试时先看 `%http_data` 的内容。

**验收**：`python scripts/cost_guard.py` 之外，看
```bash
curl -H "X-API-Key: <key>" "http://127.0.0.1:18787/aggregate?domain=phone&day=$(date +%F)"
```

## 关于「第三个手机」的说明

你的需求里同时勾了 Apple Health 和 Android，还有消费记账。
这三件事互不冲突，但**优先级差很多**：

- **消费记账** → 用 **Firefly III**（有官方 REST API + Personal Access Token）。
  别用 Actual Budget，它**没有原生 HTTP API**，要第三方 wrapper 才能读。
  接进来之后可以在日记里加一段「今日支出」。
- **Apple Health** → 只有你确实有 iPhone 才需要。纯 Android 的话
  `sources.apple_health.enabled: false`，整条链路（Health Auto Export 的
  Premium 订阅、ingester、MCP）全部省掉。
- **Android 健康** → Health Connect 自带导出只能生成加密 ZIP 到云盘、
  且只能定时。要本地 JSON 得靠第三方 App（Health.md 能直接 POST 到自建端点）。

**建议顺序**：先做 1 → 看一周 → 再决定 2/3/5 哪个对你真的有用。
