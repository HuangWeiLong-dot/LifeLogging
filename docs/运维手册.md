# 运维手册

## 每天要跑的东西

两个计划任务，分工不同（注册见 `scripts/setup_scheduler.ps1`）：

```
每 2 小时  LifeLogging-Refresh   run_daily.ps1 -Refresh
           └─ 只拉今天：collect × 4 → normalize → 写副笔记
              不调 AI、不推进水位线。就是把「双击 更新数据.cmd」自动化掉

23:00      LifeLogging-Daily     run_daily.ps1
每次解锁    ├─ cost_guard gate          预算预检
           ├─ collect_desktop.py       ActivityWatch（窗口标题 / AFK / 浏览器 URL）
           ├─ collect_phone.py         Dawarich
           ├─ collect_phone_events.py  服务器中继（手机使用事件）
           ├─ collect_watch.py         服务器中继（Gadgetbridge 导出）
           ├─ ingest_gadgetbridge.py   手环
           ├─ normalize.py             规则归类 → 时间轴
           ├─ push_journal_input.py    把「日记输入」推给服务器（见下）
           ├─ pull_journal_output.py   取回服务器写好的日记，组装进 vault
           ├─ generate_questions.py    次日要问的问题 → 推到中继
           └─ apply_answers.py         回收昨天问出去、今早答回来的
           周日额外：reconcile_cost.py
```

## 站点实时聚合（LifeLogging-Live）

站点 LIFE 页的图表读的是 `https://cms.liveinpassion.me/api/life`。
除了上面 23:00 的正式发布，还有一条轻量实时链路：

```
每 2 分钟   LifeLoggingLive.exe run_live.ps1  （Windows：无窗口守护程序，见下）
           （旧的 LifeLogging-Live 计划任务已停用，避免每次闪 PowerShell）
            ├─ collect_desktop.py --date today
            ├─ collect_phone_events.py --date today
            ├─ normalize.py --date today            （回写 blocks，聚合才会动）
            ├─ publish_life_site.py --date today    （只 upsert 今天，不碰水位线）
            ├─ publish_live_now.py                  （/api/life/now：位置/问答/电脑/手机/手表）
            └─ 每 15 分钟再做：Dawarich 位置 / Gadgetbridge / push_health / AI 账单
```

`publish_live_now.py` 在发布前会用 `translate.Translator` 把中文（实时问答原文、窗口标题、
地名）翻成英文，缓存 + 单轮上限 6 条；站点是英文界面，**不要**直接发中文。
`/api/life/now` 是公开接口，**故意含当前坐标**，和 `/api/life` 的“不含坐标”边界不同。

- 注册：`powershell -File scripts\setup_live_task.ps1`（每 2 分钟，重采集 15 分钟）。
  **Windows 当前实际用的是 `windows/live-daemon/` 里的 LifeLoggingLive.exe**：
  它没有控制台，登录后从启动文件夹自启，每 2 分钟用隐藏子进程调用同一个
  `run_live.ps1`；`LifeLogging-Live` 任务已被停用。安装 / 卸载见
  `windows/live-daemon/README.md`。不要为了“再注册一次”去重跑
  `setup_live_task.ps1`，那会重新启用会闪窗的任务。
- 它**不调 AI 写日记、不推进水位线**；23:00 的 `LifeLogging-Daily` 仍然是正式闭环。
- 原始归档（raw：日记 / 坐标 / 窗口标题）默认**不实时发**：
  `publish_life_raw.py` 会调 LLM 翻译，而且实时发布会把当前坐标公开。
  需要时给任务参数加 `-RawMinutes 30`（见 `run_live.ps1` 头部说明）。
- 手表步数/心率依赖手机把 Gadgetbridge 导出传到中继；如果手机还没传，
  站点今天的 `steps` 会是 `—`，这不是发布链路坏了。
- 站点 NOW 的手表卡优先读本机 `events.db`（本地 / 中继取 `day` 更新的一份，
  同日优先本地）；中继 `/watch` 只是给飞书机器人的那份。实时轮的
  `push_health.py` 会把它补齐，别只在 `run_daily` 里跑。
- 日志：`state/logs/live_<date>.log`（只保留 7 天）。
- **笔记本关机后**由服务器上的 `lifelogging-live-now.timer`（`server/live-now/`）
  每 2 分钟继续发 NOW：位置来自 Dawarich、手机/问答来自中继、手表直接解析中继上的
  `gadgetbridge.db`；电脑窗口只能停在最后一份 `/desktop` 快照。部署见
  `server/live-now/README.md`。
- 卸载：`Unregister-ScheduledTask -TaskName "LifeLogging-Live" -Confirm:$false`

**AI 写日记那一步在服务器上，不在本机。** 本机只负责推输入、取输出：

```
每 15 分钟  lifelogging-close-day.timer（服务器）
           └─ close_day.py   扫最近 3 天：有「终版输入」还没生成的那天 → 调 AI
                             写正文 → 存回中继。**完全不碰 vault。**

本机流水线  ──push_journal_input.py──►  中继 journal-input-<day>.json
                                        （final=true 表示这天已经过完、可以写了）
            ◄──pull_journal_output.py── 中继 journal-output-<day>.json
                                        （正文 + 用量统计，本机组装进 vault）
```

> ⚠️ **为什么「取日记」放在日循环外面。** 水位线管的是「采集有没有做完」，
> **不是**「AI 日记有没有写好」。把两者绑在一起，取不到时就只能二选一：
> 谎报成功（那份日记永远丢了），或者谎报失败（每天早上报红，很快你就不看了）。
> 所以它和 cost-events / questions 一样尽力而为，往前扫 3 天，自身幂等。
>
> ⚠️ **推的 `final` 标记是关键。** ActivityWatch 保留完整历史，但笔记本只在
> 开机时才推 —— 如果它 18:00 就关机了，服务器手里那份只到 18:00。所以只有
> 「这次处理的这一天已经过完」时才标 `final`，服务器见到它才写。**宁可不写，
> 也不拿半截数据写日记。**

> 提问那两步只对**最新的一天**做，而且 `-Refresh` 模式下不生成问题
> （`-SkipAI` 时跳过 LLM 调用）—— 补跑 5 天不该生成 5 份过期问题，
> 何况中继只认最新那一份。详见下面的「每日提问」一节。

> ⚠️ **为什么必须有 Refresh 这个任务。** `LifeLogging-Daily` 白天必然什么都不做：
> 水位线逻辑规定「今天只在 23:00 之后才被正式处理」（否则早上补跑会把只用了
> 半天数据的一天标成已完成，那一整天就再也不会重跑）。而 23:00 那次需要机器
> 那时开着 —— 这台笔记本多半已经关机或睡眠（`WakeToRun=False`，有意不唤机器）。
> 实测 10-14 那天 22:18 就关机了，23:00 那次根本没机会跑；剩下的自动运行全是
> 白天的解锁触发，它们一律印 `Nothing to do`。**没有 Refresh 的话，当天的数据
> 永远不会自己出现。**

**想知道它到底跑没跑**（两个任务都跑在隐藏窗口里，看不见）——看
`state/last_run.md`：本次运行的摘要 + 最近 15 次运行的时间线。
真处理了东西或失败会弹系统通知；每 2 小时的例行刷新不弹。

日志在 `state/logs/run_YYYY-MM-DD_HHMMSS.log`，保留 30 天。

> ⚠️ 它的数据目录 `/var/lib/lifelogging/` 是手机使用事件的**原始唯一副本**

## 排障

### 「今天日记是空的 / 内容很少」

按这个顺序查：

```bash
# 1. 采集端有没有数据
python scripts/collect_desktop.py --date today

# 2. 事件表里到底有什么
curl -H "X-API-Key: <key>" http://127.0.0.1:18787/days

# 3. 归一化结果
python scripts/normalize.py --date today
cat state/timeline-$(date +%F).md
```

90% 的情况是 **ActivityWatch 没在跑**，或者 `APP_RULES` 没覆盖你的常用软件
（看 timeline.md 末尾的「规则没认出来的应用」）。

### 「分类不准」

改 `normalize.py` 的 `APP_RULES`。规则是「小写子串包含」，
把更具体的关键词放前面。改完重跑 normalize 即可，不用动 AI。

如果 AI 也判错了，改 `generate_journal.py` 的 `SYSTEM_PROMPT` 里的边界规则。
**注意**：改系统提示词会让当天的 prompt cache 失效，那天会贵一些。

### 「费用比预期高」

**先分清是哪个费用** —— 这两个数差两个数量级，混起来会白查半天：

```bash
python scripts/collect_ai_usage.py --dry-run   # 账号真实支出（含 Claude Code 等所有工具）
python scripts/cost_guard.py report --days 7   # 只有本流水线自己
```

- 如果是**账号总额**高：多半跟本系统无关 —— 你白天用 Claude Code / 编辑器
  花的是同一把 key、同一个余额。去 Grafana 的「生命记录 · AI 用量」看按模型的拆分。
- 如果是**本流水线**高，再往下看：

看两个数：
- **缓存命中率** —— 低于 30% 说明 prompt caching 没生效。
  检查系统提示词是不是每天都在变（比如把日期拼进了 system 而不是 user）
- **每日调用次数** —— 超预期说明流水线被重跑了多次

降本手段（按效果排序）：
1. 多写 `APP_RULES`，规则覆盖率上去就不用 AI 兜底
2. 检查缓存命中率
3. 换 `claude-haiku-5-5` 跑分类，只在写复盘时用大模型（要改代码，未实现）
4. `max_output_tokens` 调小

**余额快见底了怎么办**：`cost_guard.py check-deepseek` 会用**余额差**算还能撑几天
（要两天以上样本；只有一个样本时它会明确说那个数只覆盖本流水线）。
余额归零 = 当晚日记直接生成失败，且会连续失败。

### 「AI 用量页上的精确金额空了」

那几格靠 `DEEPSEEK_USER_TOKEN`（DeepSeek 平台的**登录态** token，不是 API key）。

```bash
python scripts/collect_ai_usage.py    # 报 401 就是 token 过期了
```

重新拷一个：浏览器打开 platform.deepseek.com → F12 → Application → Local Storage →
`userToken` → 复制 `value` 字段 → `setx DEEPSEEK_USER_TOKEN "..."` → 重开终端。

⚠️ 它是登录凭证、等于你的账号：别提交、别外传、别贴进聊天记录。
不配也能跑，只是退化成「余额 + 估算」，精确金额那几格一直是空的。

### 「Dawarich 突然收不到位置了」

Android 后台限制是常态，不是 bug。依次检查：

1. 手机上 GPSLogger 的**「忽略电池优化」**还在不在（系统更新会重置）
2. 位置权限有没有从「始终允许」退回「仅使用时允许」（**这个最常见**）
3. 厂商自启白名单里 GPSLogger 还在不在
4. 服务器地址通不通（Tailscale 断了？）

参考 [dontkillmyapp.com](https://dontkillmyapp.com/) 上你机型的具体设置。

### 「.ps1 报 Missing closing '}'，但那个位置明明是对的」

**这是编码问题，不是语法问题。**

Windows PowerShell 5.1 读取 `.ps1` 时，如果文件**没有 BOM**，会按系统 ANSI 代码页
（中文系统是 GBK）解码。文件里的中文是 UTF-8 字节，被当成 GBK 解码后会错位配对，
**吃掉后面紧跟的 ASCII 字符 —— 包括大括号和引号**。于是解析器看到的代码和你看到的不一样，
报错行号还会指向一个完全无关的地方。

症状：报错行和你肉眼看到的内容对不上（差几行）。

确诊：
```powershell
# 无 BOM 会 FAIL，加 BOM 会 PASS —— 同一个文件，唯一变量是 BOM
$e = $null
$null = [System.Management.Automation.Language.Parser]::ParseFile(
    'C:\完整\路径\xxx.ps1', [ref]$null, [ref]$e)
if ($e.Count) { $e[0].Message } else { 'PASS' }
```

修复：把文件存成 **UTF-8 with BOM**。
```powershell
# PowerShell 里转
$p = 'C:\path\to\LifeLogging\scripts\run_daily.ps1'
$c = Get-Content $p -Raw -Encoding UTF8
[System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding $true))
```

⚠️ **用编辑器（含 VS Code 的默认设置、大部分 Git 工具）改这些脚本后要复查 BOM。**
本项目所有 `.ps1` 都已带 BOM，改完跑一次：
```powershell
powershell -NoProfile -File scripts\check_ps1.ps1
```

### 「某一天的记录整个没了 / 23:00 那次没跑」

先打开 **`state\last_run.md`** —— 它列了最近 15 次运行的时间线和每次的结论，
一眼就能看出跑没跑。要更细的再往下：

先确认到底跑没跑 —— **别靠猜**：

```powershell
# 最后一次跑是什么时候、结果如何
Get-ScheduledTask -TaskName 'LifeLogging-Daily' | Get-ScheduledTaskInfo
#   LastRunTime / LastTaskResult / NumberOfMissedRuns

# 机器最后一次开机是什么时候
(Get-CimInstance Win32_OperatingSystem).LastBootUpTime

# 睡眠 / 唤醒历史（42 = 进入睡眠，107 = 唤醒）
Get-WinEvent -FilterHashtable @{LogName='System';
  ProviderName='Microsoft-Windows-Kernel-Power'; Id=42,107} -MaxEvents 40 |
  Select-Object TimeCreated, Id
```

任务的触发条件（`scripts/setup_scheduler.ps1`）：

| 触发器 | 什么时候跑 |
|---|---|
| 每日 23:00 | 机器醒着时 |
| 解锁时（延迟 30 秒） | 每次解锁 |

所以「记录没了」有两种成因。第一种就是下面这段：**23:00 那一刻机器在 S3 睡眠或关机，
而且之后一直没解锁过**。第二种是「跑了，但一行都没落盘」，见本节末尾两小节。

关键事实：`WakeToRun = False`，**这个任务唤不醒机器**（有意的 —— 不想让笔记本半夜自己亮）。
23:00 时机器在睡，任务就不会跑；靠解锁触发器在你下次开盖时补上。
`run_daily.ps1` 是水位线 + 幂等的，无事可做会立刻 `exit 0`，所以「每次解锁都跑一遍」几乎零成本。

> ⚠️ **别把「没重启」当成「没跑」。** 传统 S3 睡眠下系统是挂起的、定时器不跑；
> 但机器如果一直醒着（合盖没生效、被外设反复唤醒等），23:00 照样会跑。
> 实测这台机器的历史正好说明「跑成了」不等于「机制生效」：
> 连续运行 10 天没重启，而 2.5 个月里 100 次睡眠尝试**没有一次超过 60 秒** ——
> 它其实一直醒着，任务能跑是碰巧。真正的洞一直在，加了解锁触发器才补上。
> （原来只靠 `StartWhenAvailable`，而那个补跑要等**下一次开机**；机器只是合盖睡了、
> 并没有重启的话，就没有这个触发点。）

> 📌 **为什么解锁触发器要用 XML 注册。**
> `New-CimInstance -CimClass MSFT_TaskSessionStateChangeTrigger -ClientOnly` 造出来的实例
> `Register-ScheduledTask` 一律拒收：`0x80070057 The parameter is incorrect` ——
> 带不带属性、单独传还是和每日触发器一起传，四种组合全试过，全失败。
> 而 `New-ScheduledTaskTrigger` 这个 cmdlet 不支持会话状态变更触发器。
> 所以 `setup_scheduler.ps1` 先按对象式注册，再 `Export-ScheduledTask` → 插入一段触发器
> → 用 `-Xml` 重新注册。好处是结果可以直接 `Export-ScheduledTask` 核对，不是黑箱。
>
> 另注：CIM 里 `SessionUnlock` 的数值是 **8**（不是大多数人以为的 6），
> 所以 XML 里写符号名 `SessionUnlock`，别写数字。

### 「跑了，但报失败：events API 起不来」

`run_daily.ps1` 现在会在事件表连不上时直接 `exit 1`，日志末尾长这样：

```text
BLOCKED events API is not reachable -- refusing to process any day.
        uvicorn said (state\logs\events_api.err.log):
          ERROR: [Errno 13] error while attempting to bind on address
          ('127.0.0.1', 8787): [winerror 10013] ...
```

`WinError 10013` = **端口被系统保留了**，不是你代码的问题。
Windows 的 TCP 动态端口池是 1024–15000，Hyper-V / WSL 每次开机都会从里面划走几段：

```powershell
netsh int ipv4 show excludedportrange protocol=tcp
```

划走哪几段是**随机**的 —— 所以典型症状是「昨天还好好的，今天开机就起不来了」。

**端口必须留在 15000 以上**（现在是 18787，见 `config.yaml` 的 `sources.events_api.api_base`）。
别改回 8787 这类低位端口，下次重启就可能再被划进去。改端口时这几处要同步：
`config.yaml`、`middleware/events_api.py` 里 `_bind()` 的兜底默认值、以及文档里出现的旧端口号。

> `run_daily.ps1` 之所以 `exit 1` 而不是继续：采集脚本会把「连不上事件表」当降级处理、
> 照样 `exit 0`（那对「手表没戴」是对的，对「落盘的地方没了」是错的）。
> 继续跑下去只会把这一天标成「已完成」，然后它就再也不会被重跑。

### 「跑了，也报成功，但库里还是没有」

先看**库里到底有没有**，别只看日志。数的时候用 `day_local` 这一列：

```powershell
.venv\Scripts\python.exe -c "import sqlite3;c=sqlite3.connect('state/events.db');print(c.execute('select day_local,count(*) from events group by day_local order by day_local').fetchall())"
```

> ⚠️ **别按 `ts_utc` 分组。** 一天的归属看 `day_local`。本地的 15 号是 UTC 的
> `14 号 16:00Z → 15 号 16:00Z`；按 `ts_utc` 数会把半夜那几个小时算进前一天，
> 看起来就像「昨天已经录好的数据被改写了」，其实是自己数错了。

如果日志说成功、库里却是空的，检查水位线有没有被错误推进：

```powershell
Get-Content state\last_processed.json
```

`last_date` 一旦越过某一天，自动模式就**不会**再回头处理它，只能手动补：

```powershell
powershell -NoProfile -File scripts\run_daily.ps1 -Date 2026-10-14
```

手动模式（`-Date`）不推进水位线，所以补跑不会掩盖问题，也不会重复记账。

### 「提问机器人没动静」

链路有四处，从后往前查，每一处都有明确的观察点：

```powershell
# 1. 问题生成了吗（本机）
dir state\questions-*.json
type state\questions-2026-10-14.json

# 2. 中继上有没有、还剩几条（注意：这会消耗掉当天的提醒，见下面的警告）
curl -H "X-API-Key: <key>" http://<服务器Tailscale地址>:8788/ask/pending

# 3. 答回来了吗、能不能对上任务表（--no-write 只打印，不动文件）
.venv\Scripts\python.exe scripts\apply_answers.py --date 2026-10-14 --no-write
```

| 症状 | 原因 |
|---|---|
| `state\questions-*.json` 不存在 | ① 那次运行带了 `-SkipAI`（`-Refresh` 模式就是）；② 生成失败了，看 `state\logs\run_*.log` 的 `questions` 步骤。**日记没生成已经不再是理由** —— 2026-10-19 起会用任务表 + 时间线兜底 |
| 没生成提问但**任务表里明明有 todo** | 看日志里的 `Material:` 和 `Quota:`。现在日记缺失会用任务表兜底；只有任务表也是空的、常规配额又是 0 时，才真的没得问 |
| 文件在，但 `/ask/pending` 返回 `0` | 中继只认**最新**那一份，可能已经有更新的；或者已经提醒过一次了（读一次就归零） |
| `/ask/pending` 有数字，手机却没弹 | Tasker 那个 Profile 没配好，或被 Android 杀了后台 —— 和那 4 个采集 Profile 一样要设「忽略电池优化」 |
| 答了，但任务没被勾掉 | 看第 3 步的输出：每条答案都会打出来，对不上的会打 `⚠️ 对不上任务表里任何一条`。那说明模型给的 `ref` 和任务表里的原文写法不一致 —— 它被要求逐字照抄，所以这通常意味着任务表的原文被改过了 |

> ⚠️ **`/ask/pending` 是「读一次就归零」的。** 你拿 curl 试一下，就等于把
> 当天的提醒消耗掉了 —— 手机之后再轮询也拿不到数字。想看一眼又不消耗它，
> 用 `?again=1`：它只清标记、自己不算一次读取，所以你能看到条数，
> 而手机下次轮询仍会照常提醒。

> 📌 **Tasker 那一侧我没法验证**，只能给你步骤（见
> `server/phone-relay/README.md` 的「每日提问」一节）。中继的四个端点和
> 本机的两个脚本都是实测过的，所以如果链路断了，先怀疑手机那一环。

### 「某天一直没写日记 / 水位线不动」

先看本机的 `state\journal-final-<day>.json`：

```powershell
type state\journal-final-2026-10-18.json
type state\last_processed.json
```

| 内容 | 含义 |
|---|---|
| 文件不存在 / `relay_ok=false` | 输入包没推成功。查中继地址、key、`systemctl status lifelogging-relay` |
| `final=false` | 23:00 那次本来就不是终版（`end_local` 是 23:59:59.999999）。等午夜后的运行重新处理；或手动 `powershell -File scripts\run_daily.ps1 -Date 2026-10-18` |
| `final=true, relay_ok=true` 但还没日记 | 服务器没写。看 `journal-input-<day>.json` 里的 `final`，以及 `journalctl -u lifelogging-close-day`、中继的 `journal-output-<day>.json` |

> 第二天早上直接 `Nothing to do` —— 于是这一天永远不会再被补推终版。

### 「复盘里没有白天的实时回答」

### 「某个任务在 10/14/18/21 点没被问」

实时任务检查依赖服务器的 `journal-input-<day>.json` 里的 `tasks` / `carryover`，
而它由笔记本推送。如果笔记本整天没醒，服务器会拿最近 2 天内最新的那份。
检查：

```bash
ls -lt /var/lib/lifelogging/journal-input-*.json | head
python3 - <<'EOF'
import json
d=json.load(open('/var/lib/lifelogging/journal-input-2026-10-18.json'))
print("tasks:", d.get("tasks"))
print("carryover:", d.get("carryover"))
EOF
```

没有任务时脚本会回退成普通小时题，不会报错。

### 「一天的活动只剩几个小时 / 日记里的时间线对不上」

先看两个数字：

```bash
python scripts/normalize.py --date 2026-10-13
# 输出里这两行：
#   ✓ 645 slices, span 18:42 → 22:05
#   ✓ Merged into 39 time blocks → 22 after folding the short ones in
#   -> Category totals: ... TOTAL 2.34h
```

**`span` 的时间和 `TOTAL` 的时间差太多**（比如用了 3.4 小时只入账 0.4 小时），
就是时间在 `normalize.py` 里被吃掉了。

历史上这里有过两个真实缺陷，都修了，但值得知道它们长什么样：

1. **`MIN_BLOCK` 是过滤器而不是折叠器。** 短于 6 分钟的时间块被 `continue`
   直接丢掉，一天 2.34 小时的活动只剩 0.41 小时入账，**82% 无声消失**。
   现在短块会被并进相邻块（`fold_short_blocks`），总量守恒。

2. **「规则没认出来」被当成「换了一件事」。** 合并判据要求分类完全相同，
   于是 `Work → Other → Work → Other` 这种交替把连续活动切成上百个碎片。
   现在 `Other` 只表示「没有信息」，同一应用且时间连续就延续当前活动；
   短于 15 秒的异类块（焦点闪动）同样不构成切换。

**这两个问题的下游后果最值得警惕**：日记模型拿到的正常时间块太少，
它会**编造时长来填满** Time Log。实测它写出过「19:16-21:11 [2h]」这种
数据里根本不存在的区间（真实数据在那个窗口只有 4 分钟）。
现在 `generate_journal.py` 有个硬闸门：模型写的总时长与规则引擎相差超过
`MAX_DEVIATION`（60%）就**拒绝写出**，退出码非 0、水位线不推进、下次自动重来。

> 要判断一份历史日记是不是编的，看 `vault/06-AI-Sessions/<日期>.md` 里那条
> 「Model total X vs rule-engine total Y」的警告 —— 差值超过 100% 的都要怀疑。


**可以重建的**（不用备份）：
- `state/timeline-*.md/json` —— 重跑 normalize 就有了
- `state/logs/` —— 日志
- ActivityWatch 的原始桶 —— 重装可采，但历史就没了（所以还是建议一起备份）

### 磁盘占用

本方案**不录屏不录音**，所以没有大文件。ActivityWatch 的 SQLite 是纯文本窗口记录，
一年也就几十 MB 量级，不用操心。

（如果将来重新开启 screenpipe：默认约 30GB/月，那时才需要配置
`--fps`、`--video-quality`、`--retention-days` 来控制。）

### 隐私边界

| 数据 | 存在哪 | 会离开本机吗 |
|---|---|---|
| 窗口标题 / AFK / 浏览器 URL | `%LOCALAPPDATA%\activitywatch\` | ❌ |
| 位置轨迹 | 你的服务器 | ❌（除非 Dawarich 用了第三方 geocoding） |
| 健康数据 | 本机 SQLite | ❌ |
| 日记 | Obsidian 库 | ❌ |
| **送给 AI 的摘要** | Anthropic API | ⚠️ **会** |

**本方案不含屏幕/麦克风录制** —— 没有屏幕截图、没有音频文件、没有键盘记录。

电脑端采集到的全部内容是：
- **窗口标题字符串**（如 `main.py - LifeLogging - Code`）
- 装了 `aw-watcher-web` 扩展后，额外有**访问的 URL 和页面标题**

关于浏览器扩展的边界（值得说清楚，因为它采的是 URL）：
- 扩展只上报**当前活动标签页的 URL 和标题**，**不读页面内容、不截屏、不记录表单输入**
- **隐私/无痕窗口会被显式跳过**（代码里 `if data.get("incognito"): continue`），
  所以无痕里的访问不会被记录
- 只记录**活动标签页**，后台标签页不计时
- 它把数据发到 `http://localhost:5600`，也就是本机的 ActivityWatch，不出网

⚠️ 装扩展时注意**商店里有同名冒牌货**。只认官方 ID：
`nglaklhklhcoonedhgnpgddginnjdadi`（ActivityWatch）。另一个同名的
`fdlchjabjccnihpndlmkfobegggjpnhi`（Enfiniti Group）不是官方的 ——
装错等于把你访问的每一个 URL 送给不明第三方。

**最后一行是唯一的例外，要清楚**：日记生成时，时间轴摘要会发给 Anthropic。
摘要包含窗口标题（可能含文件名、聊天对象名）。要避免的话：

1. `ai.provider: ollama` —— 完全本地，零外传
2. 或在 `build_user_prompt` 里加脱敏：把窗口标题里的敏感词替换掉

Dawarich 的逆地理编码是内置的（本地做），不像 Reitti 默认走官方托管服务 ——
这也是当初选 Dawarich 的理由之一。

## 补跑历史数据

流水线漏跑一天：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_daily.ps1 -Date 2026-10-12
```

⚠️ 但**采集端的数据可能已经过期**：
- ActivityWatch 是持久化的，补跑没问题
- Dawarich 同理，补跑只能拿到服务器上还留着的
- **手环数据**要从 Gadgetbridge 的导出文件补，所以那个文件的保留策略要宽松

所以：漏跑当天就尽快补，别拖。

> ⚠️ **补跑会消耗「今天」的预算额度**，不是被补那天的。
> 台账记的是调用实际发生的时间戳（`common.py` 里用 `datetime.now()`），
> 因为预算管的是「你今天花了多少钱」，跟数据归属哪天无关。
> 一口气补 5 天就会连扣 5 次钱 —— 补跑前先看一眼 `cost_guard.py status`。
