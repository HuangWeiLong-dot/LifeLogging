# 实现文档

**这份文档记录系统实现了什么、记录了哪些数据、数据怎么流动。**
（和另外三份的区别：`分阶段落地.md` = 怎么从零搭起来；`运维手册.md` = 出问题怎么查；`扩展路线图.md` = 以后想加什么。）

最后更新：**2026-10-14**

---

## 一、系统一句话

把电脑、手机、手表上**可记录的数据**自动采集 → 归一成一张长表 → 每晚用 AI 生成结构化日记，写进 Obsidian。

**设计原则**：数据全部本地 / 自托管，不依赖第三方云；不含屏幕录制和录音。

---

## 二、架构：三台机器，各司其职

```
┌─ 采集层 ─────────────────────────────────────────────────────────┐
│                                                                  │
│  电脑 Win11          ActivityWatch                               │
│                      窗口标题 / AFK / 浏览器 URL ──┐              │
│                                                    │              │
│  手机 Android        Tasker                        │              │
│                      解锁 / 切应用 / 屏幕亮灭 ──┐   │              │
│  手机 Android        Gadgetbridge                 │   │              │
│                      步数 / 心率 / 跑步 ────────┤   │              │
│  手机 Android        GPSLogger                    │   │              │
│                      位置点 ────────────────────┤   │              │
│                                                 │   │              │
│                              ┌──────────────────┘   │              │
│                              ↓                      │              │
│                      服务器（常驻）                  │              │
│                        · Dawarich（位置）            │              │
│                        · phone-relay（手机/手表）    │              │
│                              │                      │              │
└──────────────────────────────┼──────────────────────┼──────────────┘
                               │   每晚 23:00 笔记本主动拉取
                               ↓                      ↓
                    ┌──────────────────────────────────────┐
                    │  本机统一事件表  state/events.db      │
                    │    events（长表） + blocks（分类后）  │
                    └──────────────┬───────────────────────┘
                                   ↓
                   normalize（规则分类）→ generate_journal（AI 写日记）
                                   ↓
                              vault/  Obsidian
```

### 为什么要有那台服务器

**笔记本一天只醒几小时**（实测 2026-10-13：24 小时里 ActivityWatch 只采到 3.4 小时）。
而手机上的上报工具（Tasker、GPSLogger）**没有队列** —— 笔记本睡着时那一发直接失败，数据静默丢失。

所以手机只对**一台 24 小时在线的设备**说话，笔记本醒着的时候主动来拉。

| 机器 | 角色 |
|---|---|
| Win11 笔记本 | 采集（有 GUI 的）+ 跑每晚的流水线 |
| Linux 服务器 | 常驻接收端（Dawarich + phone-relay） |
| 手机 | 采集 + 上报 |

## 三、数据字典 —— **记录了哪些数据**

全部落在 `state/events.db` 的 `events` 表里。一条记录的形状：

```
ts_utc | day_local | domain | metric | value_num | value_text | source | meta_json
```

| domain | metric | 来源 | 单位 | 含义 |
|---|---|---|---|---|
| `screen` | `app_usage` | ActivityWatch | 秒 | 某个应用的窗口用时 |
| `screen` | `afk` | ActivityWatch | 秒 | 没在电脑前 |
| `web` | `page` | aw-watcher-web | 秒 | 页面标题 + URL 的用时 |
| `web` | `site_usage` | aw-watcher-web | 秒 | 按站点聚合的用时 |
| `location` | `tracked_points` | Dawarich | 个 | 当天轨迹点汇总（含中心/跨度/首末点） |
| `location` | `visit` | 本地停留检测 | 分钟 | 停留点（Dawarich 自己的 `/visits` 恒为空，所以自己推） |
| `location` | `transport` | Dawarich `/tracks` | 分钟 | 真正在移动的段（原地不动的不算） |
| `phone` | `unlock` | Tasker | 次 | 屏幕解锁 |
| `phone` | `app_switch` | Tasker | 次 | 应用切换（`value_text` = 包名） |
| `phone` | `screen_on` | Tasker | 次 | 屏幕亮 |
| `phone` | `screen_off` | Tasker | 次 | 屏幕灭 |
| `health` | `steps` | Gadgetbridge | 步 | 当天累计步数 |
| `health` | `heart_rate_avg` / `_min` | Gadgetbridge | bpm | 全天心率 |
| `health` | `run_km` / `run_minutes` / `run_count` | Gadgetbridge | km / min / 次 | 当天跑步汇总 |
| `health` | `run_pace_s_per_km` | Gadgetbridge | 秒/公里 | 合并配速（283 = 4:43/km） |
| `health` | `vo2max` | Gadgetbridge | ml/kg/min | 最大摄氧量 |
| `fitness` | `workout` | Gadgetbridge | 分钟 | **单次**锻炼（距离/配速/心率区间/爬升/卡路里/恢复时间都在 `meta_json`） |
| `ai` | `cost_reconcile` | reconcile_cost.py | 元 | 与厂商账单对账的差额 |

### 几个**刻意**的设计

**`fitness` 和 `health` 分开。** 单次锻炼（`fitness`）只进事件表给可视化用；
日记要的是「今天跑了 4.2 公里」，所以汇总值走 `health`。
不分开的话，日记的 `## Health` 里会出现一行没头没尾的「workout: 20.0」。

**原始 GPS 点不存进本机。** 一天最多 1440 个点，纯属重复存储。
Dawarich 自己存着，本机只留日汇总。判断标准：**这条数据三个月后你还会查吗？**

**手机应用存包名，不存显示名。** `com.tencent.mm` 而不是「微信」。
采集层存原始值、展示层做解释（`normalize.PHONE_APPS`），
否则以后改映射就得回头改历史数据。

### 分类后的表：`blocks`

`normalize.py` 把 `events` 分类成时间块写进 `blocks`：

```
day_local | start_utc | end_utc | hours | category | app | title | url
          | confidence | blackhole | source
```

`category` 取自 `config.categories`（Work / Study / Life / Transport / Leisure / Health / Social / Other）。

**这是可视化真正要用的那一层** —— Grafana 直接读它。

## 四、每天会发生什么

```
22:00   手机 Tasker  把 Gadgetbridge 导出的 .db 上传到服务器中继
                    （比笔记本的流水线早一小时）
~随时   手机 Tasker  解锁 / 切应用 / 屏幕亮灭 → 服务器中继
~随时   手机 GPSLogger → 服务器 Dawarich

23:00   笔记本 run_daily.ps1（Windows 计划任务）
         0. 预算闸门 cost_guard（超了直接停）
         1. collect-desktop       ActivityWatch → 事件表
         2. collect-phone         Dawarich → 事件表（位置）
         3. collect-phone-events  服务器中继 → 事件表（手机使用）
         4. collect-watch         服务器中继 → 本地 .db 文件
         5. gadgetbridge          读 .db → 事件表（手表）
         6. normalize             分类 → blocks + timeline
         7. generate_journal      AI 写日记 → vault/05-Journal/
```

**任何一步失败都不中断后面的步骤** —— 采不到位置不该导致日记写不出来。

**水位线机制**：`state/last_processed.json` 记「最后成功生成日记的那一天」，
每次处理从水位线+1 到今天之间的每一天。这样关机 / 睡眠错过的日子会被补跑。

## 五、2026-10-14 这一天实现了什么

### 新增的数据源

| 数据 | 从哪来 | 怎么落地 |
|---|---|---|
| **手机使用**（解锁 / 切应用 / 屏幕亮灭） | Tasker → **服务器中继** → 笔记本 | 新增 `server/phone-relay/`、`scripts/collect_phone_events.py` |
| **手表**（步数 / 心率 / 跑步） | Gadgetbridge → 同一个中继 → 笔记本 | 新增 `scripts/collect_watch.py`；中继加文件上传端点 |
| **跑步**（距离 / 配速 / VO2max / 恢复时间…） | 同上 | `ingest_gadgetbridge.py` 新增 `BASE_ACTIVITY_SUMMARY` 的解析 |

### 新增的派生指标

- **屏幕使用时间** —— `Σ(screen_off − screen_on)`，**实测**不是推的
- **各应用使用时长** —— 相邻切换的时间差，用屏幕区间裁剪；最后一个应用由 `screen_off` 收尾
- **跑步汇总** —— 配速换算成人看得懂的 `4:43/km` 再喂给模型

### 新增的可视化

- **Grafana 三个仪表盘**（概览 / 时间与分类 / 位置），`docker/grafana/provisioning/dashboards/`
- **无头渲染验收脚本** `docker/grafana/verify_dashboards.mjs` —— 用真浏览器验，不靠 curl

## 六、修掉的真实缺陷（值得记住的）

这些都是**实测踩出来的**，不是推演。共同点是：**失败是静默的** ——
文件写出来了、退出码是 0、日志里没有报错，只是数据是错的或者没了。

| 症状 | 根因 |
|---|---|
| 日记正文被拦腰截断 | `max_output_tokens` 是「推理+正文」共享额度，撞顶没被检测。现在读 `finish_reason`，截断就**拒绝写出** |
| 日记的时间线是编的（差 607%） | 规则引擎丢掉 82% 的时间（`MIN_BLOCK` 是过滤器不是折叠器 + 「认不出来」被当成「换了件事」）。模型只能编 |
| 一天的活动只剩 0.41h（实际 2.34h） | 同上。现在短块**折叠**进相邻块，总量守恒 |
| 手机的 visit 永远是 0 | Dawarich 的 `/visits` 恒为空。改成从原始点**本地做停留检测** |
| 位置只记一个「华漕」，其实没去过 | 拿全部点的**质心**去地理编码。改成取**停留最久那一簇**的位置 |
| 手表数据全无（「可能没戴表」） | 选表只看匹配几个指标 → 选中**空表**（Gadgetbridge 会建全套设备 schema） |
| 手表时间落到 1970 | `START_TIME` 是**毫秒**，按秒解释照样是合法时间戳 |
| 日记开头多出一段游离 YAML | `compose()` 先写收尾 `---` 再追加 `health:` |
| 步数停在早上的数字 | 事件表唯一索引**不含 value_num**，第二次写被静默忽略。改成先删当天再写 |
| 应用时长整榜是 0 | 屏幕事件只覆盖它出现之后的那段，之前的被裁成 0。改成**覆盖不到就退回弱估算** |
| Grafana 面板全 "No data" | 插件前端要 `rawQueryText` 不是 `queryText`；且 `busy_timeout=0` 导致并发查询撞锁 |
| 手机连不上收件口 | `Android 11+` 禁止读别的 App 的 `Android/data/`，连「所有文件访问」都不给 |

> **每一条都加了回归测试。** 现在 `smoke_test.py` 20/20。

## 七、怎么验证系统是活的

```bash
python scripts/smoke_test.py                 # 20/20，不碰任何采集源

curl http://127.0.0.1:8787/health            # 本机事件表
curl http://<服务器>:8788/health             # 服务器中继（含文件上传时间）
curl http://localhost:3001/api/health        # Grafana

node docker/grafana/verify_dashboards.mjs    # 用无头浏览器真渲染一遍仪表盘
```

**三条通道的探活都返回 200，且中继的 `file_gadgetbridge.db.updated` 是今天**，
说明整条链路是活的。

## 八、想扩展新数据源时

`events` 表的 schema **能装下绝大多数新数据**，不用改表结构：

```sql
events(ts_utc, day_local, domain, metric, value_num, value_text, source, meta_json)
```

每一类新数据只是往 `domain` 里加一个新值。可视化那边自动就能读到。

**但先问自己一句**：这条数据你三个月后还会去查吗？
不会的话，**存汇总而不是原始值**。
