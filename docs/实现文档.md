# 实现文档

**这份文档记录系统实现了什么、记录了哪些数据、数据怎么流动。**
（和另外三份的区别：`分阶段落地.md` = 怎么从零搭起来；`运维手册.md` = 出问题怎么查；`扩展路线图.md` = 以后想加什么。）

最后更新：**2026-10-14**

---

## 一、系统一句话

把电脑、手机、手表上**可记录的数据**自动采集 → 归一成一张长表 → 每晚用 AI 生成结构化日记，写进 Obsidian。

**设计原则**：数据全部本地 / 自托管，不依赖第三方云；不含屏幕录制和录音。

---

## 二、架构：三台机器，各司其职

```
┌─ 采集层 ─────────────────────────────────────────────────────────┐
│                                                                  │
│  电脑 Win11          ActivityWatch                               │
│                      窗口标题 / AFK / 浏览器 URL ──┐              │
│                                                    │              │
│  手机 Android        Tasker                        │              │
│                      解锁 / 切应用 / 屏幕亮灭 ──┐   │              │
│  手机 Android        Gadgetbridge                 │   │              │
│                      步数 / 心率 / 跑步 ────────┤   │              │
│  手机 Android        GPSLogger                    │   │              │
│                      位置点 ────────────────────┤   │              │
│                                                 │   │              │
│                              ┌──────────────────┘   │              │
│                              ↓                      │              │
│                      服务器（常驻）                  │              │
│                        · Dawarich（位置）            │              │
│                        · phone-relay（手机/手表）    │              │
│                              │                      │              │
└──────────────────────────────┼──────────────────────┼──────────────┘
                               │   每晚 23:00 笔记本主动拉取
                               ↓                      ↓
                    ┌──────────────────────────────────────┐
                    │  本机统一事件表  state/events.db      │
                    │    events（长表） + blocks（分类后）  │
                    └──────────────┬───────────────────────┘
                                   ↓
                   normalize（规则分类）→ generate_journal（AI 写日记）
                                   ↓
                              vault/  Obsidian
```

### 为什么要有那台服务器

**笔记本一天只醒几小时**（实测 2026-10-13：24 小时里 ActivityWatch 只采到 3.4 小时）。
而手机上的上报工具（Tasker、GPSLogger）**没有队列** —— 笔记本睡着时那一发直接失败，数据静默丢失。

所以手机只对**一台 24 小时在线的设备**说话，笔记本醒着的时候主动来拉。

| 机器 | 角色 |
|---|---|
| Win11 笔记本 | 采集（有 GUI 的）+ 跑每晚的流水线 |
| Linux 服务器 | 常驻接收端（Dawarich + phone-relay） |
| 手机 | 采集 + 上报 |

## 三、数据字典 —— **记录了哪些数据**

全部落在 `state/events.db` 的 `events` 表里。一条记录的形状：

```
ts_utc | day_local | domain | metric | value_num | value_text | source | meta_json
```

| domain | metric | 来源 | 单位 | 含义 |
|---|---|---|---|---|
| `screen` | `app_usage` | ActivityWatch | 秒 | 某个应用的窗口用时 |
| `screen` | `afk` | ActivityWatch | 秒 | 没在电脑前 |
| `web` | `page` | aw-watcher-web | 秒 | 页面标题 + URL 的用时 |
| `web` | `site_usage` | aw-watcher-web | 秒 | 按站点聚合的用时 |
| `location` | `tracked_points` | Dawarich | 个 | 当天轨迹点汇总（含中心/跨度/首末点） |
| `location` | `track_path` | Dawarich | 个 | **折线几何**，存在 `meta_json.path`（最多 500 点），给地图面板画路线 |
| `location` | `visit` | 本地停留检测 | 分钟 | 停留点（Dawarich 自己的 `/visits` 恒为空，所以自己推） |
| `location` | `transport` | Dawarich `/tracks` | 分钟 | 真正在移动的段（原地不动的不算）。⚠️ 模式是 Dawarich **推断**的，非实测 |
| `phone` | `unlock` | Tasker | 次 | 屏幕解锁 |
| `phone` | `app_switch` | Tasker | 次 | 应用切换（`value_text` = 包名） |
| `phone` | `screen_on` | Tasker | 次 | 屏幕亮 |
| `phone` | `screen_off` | Tasker | 次 | 屏幕灭 |
| `health` | `steps` | Gadgetbridge | 步 | 当天累计步数 |
| `health` | `heart_rate_avg` / `_min` | Gadgetbridge | bpm | 全天心率 |
| `health` | `run_km` / `run_minutes` / `run_count` | Gadgetbridge | km / min / 次 | 当天跑步汇总 |
| `health` | `run_pace_s_per_km` | Gadgetbridge | 秒/公里 | 合并配速（283 = 4:43/km） |
| `health` | `vo2max` | Gadgetbridge | ml/kg/min | 最大摄氧量 |
| `fitness` | `workout` | Gadgetbridge | 分钟 | **单次**锻炼（距离/配速/心率区间/爬升/卡路里/恢复时间都在 `meta_json`） |
| `ai` | `cost_reconcile` | reconcile_cost.py | 元 | 与厂商账单对账的差额 |
| `ai` | `daily_cost` | cost_guard.py | 元 | **本流水线自己**当天的 LLM 调用合计（从 `cost_ledger.jsonl` 按天汇总） |
| `ai` | `spend` | collect_ai_usage.py | 元 | **账号当天真实支出**，来自 DeepSeek 平台用量接口 —— 权威值 |
| `ai` | `model_cost` / `model_tokens` | collect_ai_usage.py | 元 / token | 按模型拆分的花费与用量（含请求数、缓存命中/未命中/输出） |
| `ai` | `project_tokens` / `agent_tokens` | collect_ai_usage.py | token | 按项目 / 按主会话 vs 子代理拆分（**估算**，来自 Claude Code 本地记录） |
| `ai` | `balance` | collect_ai_usage.py | 元 | 账号余额快照。两次采样做差 = 真实总消耗 |

### 事件表之外的派生层（2026-10-21 起）

| 文件 | 谁写 | 内容 | 可重算？ |
|---|---|---|---|
| `state/qa-<day>.json` | qa_client.py | 当天全部问答原文 + `dim` | ✅ 中继 `/qa` |
| `state/labels.jsonl` | collect_labels.py | 飞书自评 1–5（心情/体力/睡眠），一条一行 | ✅ 从 `qa-*.json` |
| `state/features.jsonl` | features.py | 一天一行状态向量，带 `feature_version` | ✅ 从 `timeline-*.json` + labels |
| `/var/lib/lifelogging/reflex-log.jsonl` | 飞书机器人 | 每次提醒 + 后 15/60 分钟的行为 | ❌ **观测数据，删了就没了** |

前两个是**派生层**：删掉、改字段、重跑都行。最后一个是**观测层** ——
它记的是「系统在某个时刻说了什么、之后发生了什么」，和 `events.db` 一样
需要备份；一旦丢了，那段时间就永远无法重建。

### 几个**刻意**的设计

**`fitness` 和 `health` 分开。** 单次锻炼（`fitness`）只进事件表给可视化用；
日记要的是「今天跑了 4.2 公里」，所以汇总值走 `health`。
不分开的话，日记的 `## Health` 里会出现一行没头没尾的「workout: 20.0」。

**原始 GPS 点不整份存进本机。** 一天最多 1440 个点，整份存纯属重复存储 ——
Dawarich 那边已经有全量。但**折线几何要留一条**（`location/track_path`）：
没有它地图画不出来，而「我那天到底坐的哪条线」正是这类数据最难事后补的东西。
所以是**降采样到 500 个点、存成一条事件的 `meta_json.path`**，不是一天几万行事件。
判断标准始终是：**这条数据三个月后你还会查吗？**

**手机应用存包名，不存显示名。** `com.tencent.mm` 而不是「微信」。
采集层存原始值、展示层做解释（`normalize.PHONE_APPS`），
否则以后改映射就得回头改历史数据。

### AI 花费：为什么「本流水线的台账」不等于「你花了多少钱」

这是踩过的一个真实误会，值得单独写下来。

`state/cost_ledger.jsonl` 记账非常严格（hash 链防篡改），但它**只记本流水线
自己发起的调用** —— 每晚写日记那几次。而你白天真正在花钱的是 **Claude Code**：
它跑的是**同一个 DeepSeek key、扣的是同一个余额**，却一个字节都不往我们的台账里写。

实测 2026-10-14：台账口径 ¥0.21，账号真实支出 **¥22.97**。差 **109 倍**。
两个数都没算错，只是回答的问题不同。

所以现在三处一起采（`collect_ai_usage.py`）：

| 来源 | 精确度 | 能回答什么 | 限制 |
|---|---|---|---|
| **DeepSeek 平台用量接口** | **精确**（官网同源） | 按天 × 按模型的花费、token、请求数 | 要登录态 `userToken`；官方没公开这个接口 |
| **账号余额** `/user/balance` | **精确**（只有当前值） | 真实总消耗（余额差），跨所有工具 | 没有历史，两次采样才有意义 |
| **Claude Code 本地记录** | 估算（±30%） | 花在哪个项目、主会话还是子代理 | 本地推不出精确值；只用来出形状 |

**为什么不用 ccusage**（路线图里提过）：实测它**不按 `message.id` 去重**，
而 Claude Code 会把同一次 API 响应的日志重复写十几行
（同一个 id 在 3 秒内出现 11 次、usage 完全相同）。于是当天花费被放大 **2.4 倍**，
而且它按 Anthropic 的价格表报**美元**。自己解析并按 id 去重后仍偏低约 26%
（917 条唯一消息 vs 平台 1599 次请求）—— 所以 transcript 这条路**永远只是估算**。

> 结论：**只要还靠估算，就不可能精确**。想要准确值，只能以平台自己的数为准。

**`userToken` 怎么配**（一次性）：浏览器打开 platform.deepseek.com → F12 →
Application → Local Storage → `userToken` → 复制 `value` 字段那个字符串 →
`setx DEEPSEEK_USER_TOKEN "..."`。
⚠️ 它是**登录凭证、等于你的账号**，不是 API key：别提交、别外传、会过期
（重新登录就换，脚本会报 401 让你重拷）。
不配也能跑，只是退化成「余额 + 估算」，面板上精确金额那几格是空的。

### 分类后的表：`blocks`

`normalize.py` 把 `events` 分类成时间块写进 `blocks`：

```
day_local | start_utc | end_utc | hours | category | app | title | url
          | confidence | blackhole | source
```

`category` 取自 `config.categories`（Work / Study / Life / Transport / Leisure / Health / Social / Other）。

**这是可视化真正要用的那一层** —— Grafana 直接读它。

## 四、每天会发生什么

```
22:00   手机 Tasker  把 Gadgetbridge 导出的 .db 上传到服务器中继
                    （比笔记本的流水线早一小时）
~随时   手机 Tasker  解锁 / 切应用 / 屏幕亮灭 → 服务器中继
~随时   手机 GPSLogger → 服务器 Dawarich

23:00   笔记本 run_daily.ps1（Windows 计划任务）
         0. 预算闸门 cost_guard（超了直接停）
         1. collect-desktop       ActivityWatch → 事件表
         2. collect-phone         Dawarich → 事件表（位置）
         3. collect-phone-events  服务器中继 → 事件表（手机使用）
         4. collect-watch         服务器中继 → 本地 .db 文件
         5. gadgetbridge          读 .db → 事件表（手表）
         6. normalize             分类 → blocks + timeline（含黑洞关键词判定）
         7. generate_journal      AI 写日记 → vault/05-Journal/
                                  并把日记里标的黑洞回写进 blocks
         8. cost-events           台账按天合计 → ai/daily_cost 事件（给 Grafana）
         9. ai-usage              DeepSeek 平台账单 + 余额 + Claude Code 分布
        10. publish-life         近 30 天脱敏汇总 → liveinpassion.me/life
```

**任何一步失败都不中断后面的步骤** —— 采不到位置不该导致日记写不出来。

**水位线机制**：`state/last_processed.json` 记「最后成功生成日记的那一天」，
每次处理从水位线+1 到今天之间的每一天。这样关机 / 睡眠错过的日子会被补跑。

### 发布到个人站点（`publish_life_site.py` + `publish_life_raw.py`）

`ai-usage` 之后有两条发布（`-SkipAI` 的白天刷新跳过）：

1. **聚合**：近 30 天压成每日 JSON，POST 到 `/api/life/ingest`，存 D1。
   前台 `/life` 的图表用；只有聚合数字，坐标/标题/URL/包名/正文都不进。
   其中 `location.transitMinutes` = 实测 transport + 两次停留之间 4–180min、
   相距 ≥1km 的通勤空档（扣除已识别段）—— 地铁/地下没有 GPS 点，只看实测会
   把通勤时间漏掉一大半。
2. **原始**：完整日记 Markdown、随手记、任务、问答、原始事件（含坐标与
   track_path）、分类时间块（含 title/url）、周总结，以及 vault 里的主任务
   清单 / 周回顾 / 成本台账 / AI 会话日志，POST 到 `/api/life/raw/ingest`，
   存 R2。前台 `/life/archive` 用；**不脱敏**。

原始数据只做一件改动：URL 里像 token/state/code/part 的 query 值、
`sk-`/`ghp_`/`AKIA` 这类 key、Bearer 头会替换成 `REDACTED`，避免登录凭证
被永久公开。两条发布都幂等，每晚重发可自愈漏跑的日子。

**发布层翻译**：两条发布在发送前都会用 DeepSeek 把中文内容翻成英文（只改
发出去的副本，本机原文不动），缓存 `state/translation_cache.json`。
`life_site.translate_raw` / `translate_max_calls` 控制；任何一段翻译失败都会
中止本轮发布、保留线上英文版，下一轮重试。

## 七、修掉的真实缺陷（值得记住的）

这些都是**实测踩出来的**，不是推演。共同点是：**失败是静默的** ——
文件写出来了、退出码是 0、日志里没有报错，只是数据是错的或者没了。

| 症状 | 根因 |
|---|---|
| 日记正文被拦腰截断 | `max_output_tokens` 是「推理+正文」共享额度，撞顶没被检测。现在读 `finish_reason`，截断就**拒绝写出** |
| 日记的时间线是编的（差 607%） | 规则引擎丢掉 82% 的时间（`MIN_BLOCK` 是过滤器不是折叠器 + 「认不出来」被当成「换了件事」）。模型只能编 |
| 一天的活动只剩 0.41h（实际 2.34h） | 同上。现在短块**折叠**进相邻块，总量守恒 |
| 手机的 visit 永远是 0 | Dawarich 的 `/visits` 恒为空。改成从原始点**本地做停留检测** |
| 位置只记一个「华漕」，其实没去过 | 拿全部点的**质心**去地理编码。改成取**停留最久那一簇**的位置 |
| 手表数据全无（「可能没戴表」） | 选表只看匹配几个指标 → 选中**空表**（Gadgetbridge 会建全套设备 schema） |
| 手表时间落到 1970 | `START_TIME` 是**毫秒**，按秒解释照样是合法时间戳 |
| 日记开头多出一段游离 YAML | `compose()` 先写收尾 `---` 再追加 `health:` |
| 步数停在早上的数字 | 事件表唯一索引**不含 value_num**，第二次写被静默忽略。改成先删当天再写 |
| 应用时长整榜是 0 | 屏幕事件只覆盖它出现之后的那段，之前的被裁成 0。改成**覆盖不到就退回弱估算** |
| Grafana 面板全 "No data" | 插件前端要 `rawQueryText` 不是 `queryText`；且 `busy_timeout=0` 导致并发查询撞锁 |
| **时间黑洞面板永远是 0** | `blocks.blackhole` **没有任何生产代码把它设成 True** —— `normalize.py` 恒为 False，AI 在日记里标的 `[blackhole:: true]` 也不回写数据库。面板没坏，是链路从来没接上 |
| **交通方式整榜都是错的** | 那些模式是 **Dawarich 按 GPS 速度推断**的，我们只是把它的 emoji 翻译成名字 —— 等于原样转述它的结论。地铁地下没有 GPS，一段纯地铁被判成 cycling + walking + driving |
| **「出行时长」只有实际的一半** | 只统计 Dawarich 判为「移动」的段。110 分钟的通勤它只认出 50.8 分钟，其余被判成「原地」。改成用**停留点的间隔**反推 |
| **地图底图满屏「API KEY REQUIRED」** | 新版 Grafana 内置的「OpenStreetMap」底图走 Stadia，没 key 会印水印 —— 而且**不报错**。必须写显式 XYZ 瓦片地址 |
| 「今日应用时长」和「今日记录时长」对不上 | 两者是**两条独立路径**：`blocks` 由 normalize 直接读 ActivityWatch，`events` 由 collect_desktop 写入。只跑了前者时，后者就是 0 |
| 手机应用榜上混着 `%APPNAME` | Tasker 变量没替换就上报了。面板侧过滤 + 标注，根因在手机配置 |
| **「今天 AI 才花 ¥0.2」是假的（真花 ¥23）** | 台账只记本流水线自己的调用；Claude Code 用同一把 key、扣同一个余额，却什么都不往台账写。面板只看得见 **1%** 的支出。见「AI 花费」一节 |
| **「余额还能用 41 天」也是假的** | 同一根因，`cost_guard check-deepseek` 的剩余天数按台账算的。改成用**余额差**推算（需要两天以上样本），只有一个样本时明确警告「这个数只覆盖本流水线」 |
| ccusage 的用量虚高 2.4 倍 | Claude Code 把同一次 API 响应重复写十几行（同 id 同 usage），它不去重；且按 Anthropic 价目表报美元。自己按 `message.id` 去重 |
| 手机连不上收件口 | `Android 11+` 禁止读别的 App 的 `Android/data/`，连「所有文件访问」都不给 |

> **每一条都加了回归测试。** 现在 `smoke_test.py` 20/20。

## 九、想扩展新数据源时

`events` 表的 schema **能装下绝大多数新数据**，不用改表结构：

```sql
events(ts_utc, day_local, domain, metric, value_num, value_text, source, meta_json)
```

每一类新数据只是往 `domain` 里加一个新值。可视化那边自动就能读到。

**但先问自己一句**：这条数据你三个月后还会去查吗？
不会的话，**存汇总而不是原始值**。

## 十、2026-10-21：从「日志」往「状态」走了一步

这一天没有上模型，也没有上向量库。做的是模型之前必须先有的三样东西：

| 层 | 产物 | 为什么现在做 |
|---|---|---|
| 标签 | `state/labels.jsonl` | 自由文本进不了统计。心情/体力/睡眠改成 1–5 打分（其余四维仍是自由文本），**不猜**没按格式答的 |
| 状态向量 | `state/features.jsonl` | 一天一行，全部来自**已算好的** `timeline-*.json`；带 `feature_version`，缺的源是 `null` 不是 0 |
| 反射弧 | `reflex.py` + `reflex-log.jsonl` | 没人问也说话（熬夜/亮屏/娱乐/久坐/传感器哑了），并记录提醒之后 15/60 分钟的行为 |
| 历史召回 | `recall.py` + `memory-server.db` | 把服务器上已有的日记正文索引进 FTS5；「上次/以前」类问题先检索再交给模型，检索为空就直说没有 |

**三条边界，写进代码也写进测试：**

1. **样本不足就说不足。** 基线要至少 5 个历史值；过去没波动（MAD=0）就不谈
   「反常」。这和机器人里「答不了比答错好」是同一条原则。
2. **相关不是因果。** 反馈日志只记录不评价；「15 分钟没解锁」可能是听了，
   也可能是把手机放下了。
3. **只提醒，不执行。** 不做「到点关网卡」——误报一次的代价是整个系统被关掉。

**下一步（等数据，不写代码）：** 60 天后用 `labels.jsonl` + `features.jsonl`
跑带 N、带多重比较校正、带时间切分复现的关联分析；样本不够之前，
`synapses.py` 应该直接说「样本不足」而不是给一个漂亮的相关系数。
