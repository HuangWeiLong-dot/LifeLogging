> 目的：你原始需求里点名的若干工具，名字与现实有出入（有的是记错了，有的是项目性质和你以为的不一样，有的是授权状态变了）。
> **先读完这份再动手**，否则会照着一套跑不通的方案部署。
>
> 核实时间：2026-10。标注 `[已核实]` 的有官方源 URL；`[存疑]` 的只有二手来源。

## 二、屏 + 麦采集（电脑端）

### screenpipe

> **本方案已排除它**（用户明确不要录屏录音）。
> 下面这些信息保留下来，是给「将来改主意」和「理解为什么当时考虑它」用的。
> 当前的电脑端数据源只有 ActivityWatch。

| 项 | 内容 |
|---|---|
| 仓库 | `github.com/screenpipe/screenpipe`（已从 `mediar-ai/screenpipe` 迁移）`[已核实]` |
| 安装 | 官方安装器 / `npx screenpipe@latest record` / PowerShell `install.ps1`。**无官方 winget 包**，Docker 不支持（采集需要 GUI）`[已核实]` |
| 数据位置 | **`%USERPROFILE%\.screenpipe\db.sqlite`**，媒体文件在 `~/.screenpipe/data/`。可用 `SCREENPIPE_DIR` 或 `--data-dir` 覆盖 `[已核实]` |
| REST API | `http://localhost:3030`，**默认无鉴权**（可选 Bearer）。端点是 `/search`、`/activity-summary`、`/raw_sql` 等，**注意不是 `/api/search`** `[已核实]` |
| MCP | npm 包 `screenpipe-mcp`，`npx -y screenpipe-mcp`。需要 screenpipe 本体跑在 3030 `[已核实]` |
| 占用 | 官方口径：1 FPS 连续采集 ≈ 600MB RAM / ~10% CPU / ~30GB 每月；event-driven 模式 ≈ 5–10% CPU / 5–10GB 每月 `[已核实]` |
| **授权** | **Commercial License**（Negentropy Labs）。免费范围仅个人非商业/教育/研究。官方 App 是付费订阅（约 $25/月起）。无人值守或服务器部署需另签商业协议。变更前的旧版本仍是 MIT `[已核实]` |

**结论**：满足你「CPU < 15%」的要求（用 event-driven 模式）。但**授权性质要清楚**——个人自用没问题，别往服务器搬。

### 开源替代的实际情况

你想走全开源路线的话，这里有个必须接受的现实：

| 工具 | 能力 | 有 REST API？ | 有 SQLite？ |
|---|---|---|---|
| **ActivityWatch** | 窗口标题 / AFK / 浏览器 `[已核实]` | ✅ `http://127.0.0.1:5600` | ✅ |
| **OpenRecall** | 截屏 + 本地 OCR `[已核实]` | ❌ 只有本地 Web UI :8082 | ✅ 加密存储 |
| Windrecorder | 屏幕 + OCR，GPL-2.0 `[已核实]` | ❌ | — |
| ScreenMind | 屏+麦，MIT `[存疑]` | ? | ✅ 加密 |

> **没有任何一个开源工具同时做到「屏幕+麦克风采集 + 现成 API」。**
> 要么用 screenpipe（非开源但能用），要么自己拼（ActivityWatch 管窗口 + OpenRecall 管截屏，中间写胶水）。

### Windows Recall —— 直接排除

仅 Copilot+ NPU 机型；**无对外 HTTP API**；第三方读不了它的 SQLite（官方只开放了时间线 resume 联动用的 "Recall with User Activity" API，那是应用集成不是数据读取）。快照导出解密仅限 EEA 区域 + Insider 预览版 `[已核实]`。

**→ 这条路对你不可用，别浪费时间。**

## 三、位置轨迹（手机端）

### 选型：Dawarich ＞ Reitti

| | Dawarich | Reitti |
|---|---|---|
| 授权 | AGPL-3.0 `[已核实]` | MIT `[存疑]` |
| **内置 MCP** | ✅ **官方只读 MCP**，`/api/v1/mcp`，Bearer 鉴权 `[已核实]` | ❌ 未找到 |
| 原生手机 App | ✅ | ❌ 纯 Web |
| 停留点检测 | ✅ 1.8.0 起，带 0–100 置信度 `[已核实]` | ✅ |
| 交通方式推断 | ✅ walking/cycling/driving/running/train/bus/flying/boat `[已核实]` | ✅ + 手动 override |
| 逆地理编码 | 内置 | **默认走官方托管的 Paikka 实例** ⚠️ `[已核实]` |
| 社区 | ~10k★ | 小 |

**Dawarich 的 MCP 工具只有三个**：`get_timeline`（最长 7 天）、`get_latest_location`、`search_visits`。复杂查询走 REST API（`/api/v1/visits`、`/points`、`/tracks`、`/timeline`…）。

**Reitti 的硬伤**：默认用**官方托管的 Paikka** 做逆地理编码，这跟你的「数据不上第三方」原则直接冲突（要本地化得自托管 Photon/Nominatim，多一套服务）。加上没有 MCP、没有原生 App、还多一个 RabbitMQ 容器 —— 不值得。

### 客户端

**推荐 GPSLogger**（Android）：
- 可 POST 到任意 URL，格式用占位符 `%LAT %LON %TIMESTAMP %ACC %ALT %BATT %SPD`，直接指向 Dawarich 的 `/api/v1/owntracks/points?api_key=...`
- ⚠️ **v134 起「忽略电池优化」是强制要求**，不设会被系统直接杀 service `[已核实]`

OwnTracks Android 也能用，但已知 Android 14 安全补丁后 Significant Location Change 模式会静默失效，要手动把 `locatorPriority` 改成 `HighAccuracy` `[已核实]`。

**三者都支持推 generic HTTP endpoint**，所以后端不锁定。

## 四、必须写中间件的两个缺口

这两处是**真正的技术缺口**，不是配置问题：

### 1. Gadgetbridge（手环手表）—— 完全没有 REST API

- 支持小米 / Amazfit / Garmin / Pebble / Bangle 等
- 导出方式只有两条：`Settings → Automations → Auto export database`（可设每小时），或发 intent `nodomain.freeyourgadget.gadgetbridge.command.TRIGGER_EXPORT` `[已核实]`
- 导出的 SQLite 表名随设备不同（如 `MI_BAND_ACTIVITY_SAMPLES`：TIMESTAMP/STEPS/HEART_RATE/SLEEP/DEEP_SLEEP/REM_SLEEP…）
- 0.89.0 起有 Health Connect 集成，可同步 steps/HR/SpO2/HRV/体温/呼吸率/静息心率/**sleep sessions**/weight/VO2max/**exercise sessions** `[已核实]`

**→ 方案**：`middleware/ingest_gadgetbridge.py`，读导出的 SQLite → 归一进事件表。

### 2. Health Connect（安卓健康）—— 自带导出不落地

- 内建导出只能生成**加密 ZIP 到云盘**，只能日/周/月定时，**无手动导出、无本地保存** `[已核实]`
- 好消息：Health Connect API 对第三方只读开放，所以任何第三方 App 都能读并导出
- 可用第三方：**Health.md**（支持直接 POST 到自建 endpoint）、Heartwood（F-Droid，GPL-3.0，导出 CSV/JSON）

**→ 方案**：用 Health.md 或 Heartwood 导出 JSON → 喂进 events API。

## 五、AI 成本控制

### LiteLLM Proxy —— 有一个会坑死你的默认行为

> **官方原文明示**：没有 `database_url`（Postgres）时，`litellm_settings.max_budget` 是 **fail-open** —— 代理会**静默继续放行超额请求**，只在启动时打一条 warning。

**要用它做「硬封顶」就必须接 Postgres**，否则你以为设了预算，其实没有。

其他要点 `[已核实]`：
- 预算可在全局 / key / user / team / team-member 五层设置，支持多窗口（日+月并行）
- 日历窗口语义：`7d` 每周一 00:00 UTC 重置，`30d` 每月 1 日重置。**不设 `budget_duration` 则永不重置**
- 每次调用写一行到 `LiteLLM_SpendLogs` 表；响应头带 `x-litellm-response-cost`
- 告警阈值事件 `threshold_crossed` 在 **85% 和 95%** 触发
- 预算重置由后台调度器定期跑（默认约每 10 分钟）→ **跨点瞬间不精确，硬封顶要留余量**
- 报表 API：`GET /global/spend/report?start_date=&end_date=`、`GET /key/info?key=`、`GET /spend/logs`

### Langfuse（自托管）

- 能按 trace 记 cost/token，但**不能当网络层代理**（它是 observability 平台，走 SDK/OTLP 上报）。要做网关代理用 LiteLLM，再把 LiteLLM 的 callback 指到 Langfuse
- ⚠️ **已知坑**：成本估算偏高（忽略 cache pricing），有 issue 记录约 **2.83x 高估**，需显式摄入 `cache_read_input_tokens`
- v3 架构重：web + worker + ClickHouse + MinIO + Redis + Postgres，建议 ≥4 核 / 8–16GB RAM

### Helicone

据二手报道 2026-03 被 Mintlify 收购后进入 maintenance mode，OSS 自托管仍可用（Apache 2.0）但路线图冻结 `[存疑]`。
**→ 建议**：别新上，选 LiteLLM。

### 对账（替代 Tellan）

不用 Tellan（v0.1.0，9 天新）。自己写，逻辑是**三方对账**：

1. **本地侧**：`LiteLLM_SpendLogs` 或自建台账
2. **厂商侧**：Anthropic `GET /v1/organizations/cost_report`（**金额单位是「分」**，`"123.45"` = $1.23；仅支持 `bucket_width=1d`；默认延迟 ~24 小时）`[已核实]`
3. **差异**：`delta_pct = (local - vendor) / vendor`，`|delta_pct| > 5%` 告警

厂商账单 API 需要 **Admin key**（`sk-ant-admin01-...`），普通 API key 访问不了。

## 六、Windows 上的 MCP 配置陷阱

`[已核实]`

1. **npm 系的 MCP 必须用 `npx.cmd` 绝对路径**，裸写 `npx` 在 Windows 上大面积连接失败（uvx/python 系的正常）。见 `modelcontextprotocol/servers` issue #76
2. 路径要**双反斜杠**
3. 配置文件在 `%APPDATA%\Claude\claude_desktop_config.json`
4. **Obsidian 首选 `obsidian-local-rest-api` 插件**——v5.1.0（2026-08）自带 `/mcp/` 端点，免装额外 MCP。次选 npm 的 `obsidian-mcp-server`
5. `@modelcontextprotocol/server-sqlite` 官方那个**实际是 Python/uvx** 的，不是 npm。要 npm 版用 `mcp-server-sqlite-npx`
